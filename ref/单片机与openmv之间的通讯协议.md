# 一、串口基本配置

建议双方统一为：

| 参数   | 设置                 |
| ------ | -------------------- |
| 波特率 | 115200 bit/s         |
| 数据位 | 8 bit                |
| 停止位 | 1 bit                |
| 校验位 | 无                   |
| 流控   | 无                   |
| 电平   | 3.3V TTL             |
| 字节序 | 小端序 Little Endian |

STM32和OpenMV必须共地。

图像识别本身比较慢，115200波特率已经完全足够，没必要为了十几个字节的数据提高波特率。

------

# 二、统一数据帧格式

每一个串口数据包都使用以下格式：

| 字段        | 长度  | 说明                 |
| ----------- | ----- | -------------------- |
| 帧头        | 2字节 | 固定为 `0xAA 0x55`   |
| 协议版本    | 1字节 | 当前为 `0x01`        |
| 消息类型    | 1字节 | 表示具体命令         |
| 序列号SEQ   | 1字节 | 每发送一帧加1        |
| 数据长度LEN | 2字节 | Payload长度，小端序  |
| 数据Payload | N字节 | 具体数据             |
| CRC16       | 2字节 | CRC16/MODBUS，小端序 |

完整结构：

```
AA 55 | VER | TYPE | SEQ | LEN_L LEN_H | PAYLOAD | CRC_L CRC_H
```

CRC计算范围：

```
VER + TYPE + SEQ + LEN_L + LEN_H + PAYLOAD
```

不包含帧头 `AA 55`。

建议限制：

```
Payload最大长度：64字节
```

这样即使通信出错导致LEN异常，也不会一直等待一个巨大数据包。

------

# 三、为什么要同时设置SEQ和Session ID

协议中使用两种编号。

## 1. SEQ序列号

每发送一个数据包，SEQ加1，范围：

```
0～255，溢出后回到0
```

主要用于：

- ACK确认具体是哪一帧；
- 判断是否是重发包；
- 防止同一命令重复执行。

STM32和OpenMV各自维护自己的发送SEQ。

## 2. Session ID任务号

每开始一次新的完整锁相任务，STM32生成一个新的任务号：

```
uint16_t session_id
```

例如：

```
第1次任务：session_id = 1
第2次任务：session_id = 2
```

它主要用于防止这种情况：

1. 上一次识别很慢；
2. STM32已经开始新任务；
3. OpenMV突然发回上一次的结果；
4. STM32误把旧结果当成新结果。

只要收到的 `session_id` 与当前任务不一致，直接丢弃。

# 四、消息类型定义

建议这样划分消息类型：

| TYPE   | 名称               | 方向           |
| ------ | ------------------ | -------------- |
| `0x01` | ACK确认            | 双向           |
| `0x02` | NACK错误应答       | 双向           |
| `0x03` | 心跳包             | 双向，可选     |
| `0x10` | 开始识别任务       | STM32 → OpenMV |
| `0x11` | 粗识别结果         | OpenMV → STM32 |
| `0x20` | DDS频率测试命令    | STM32 → OpenMV |
| `0x21` | DDS频率识别结果    | OpenMV → STM32 |
| `0x22` | 停止当前任务       | STM32 → OpenMV |
| `0x30` | 开始相位锁定       | 预留           |
| `0x31` | 相位识别结果       | 预留           |
| `0x7F` | OpenMV主动错误报告 | OpenMV → STM32 |

# 五、ACK确认包

## 消息类型

```
TYPE = 0x01
```

## Payload格式

| 字段     | 类型  | 说明             |
| -------- | ----- | ---------------- |
| ack_type | uint8 | 被确认消息的TYPE |
| ack_seq  | uint8 | 被确认消息的SEQ  |
| status   | uint8 | 接收状态         |

`status`定义：

| 数值   | 含义                   |
| ------ | ---------------------- |
| `0x00` | 成功接收并接受         |
| `0x01` | 重复包，之前已经处理   |
| `0x02` | 已接收，但结果尚未完成 |

通常使用 `0x00` 即可。

例如，OpenMV成功接收到：

```
TYPE = 0x10
SEQ  = 0x25
```

则ACK的Payload为：

```
10 25 00
```

ACK包本身不再要求对方发送ACK，否则会出现ACK套ACK的死循环。

------

# 六、NACK错误包

## 消息类型

```
TYPE = 0x02
```

## Payload格式

| 字段       | 类型  | 说明           |
| ---------- | ----- | -------------- |
| error_type | uint8 | 出错消息的TYPE |
| error_seq  | uint8 | 出错消息的SEQ  |
| error_code | uint8 | 错误代码       |

错误代码建议：

| error_code | 含义                     |
| ---------- | ------------------------ |
| `0x01`     | 数据长度错误             |
| `0x02`     | 不支持的协议版本         |
| `0x03`     | 非法锁相模式             |
| `0x04`     | 非法锯齿波频率           |
| `0x05`     | OpenMV正忙               |
| `0x06`     | 当前状态不允许执行该命令 |
| `0x07`     | Session ID不匹配         |
| `0x08`     | 参数超出范围             |
| `0x09`     | 图像传感器错误           |
| `0x0A`     | 内部程序错误             |

CRC错误建议直接丢弃，不返回NACK，等待发送方超时重发。因为CRC都错了，TYPE和SEQ也不一定可信。

# 七、开始粗识别任务

STM32设置好锯齿波后，向OpenMV发送该命令。

## 消息类型

```
TYPE = 0x10
```

## Payload格式

| 字段        | 类型   | 长度 | 说明               |
| ----------- | ------ | ---- | ------------------ |
| session_id  | uint16 | 2    | 本次任务编号       |
| lock_mode   | uint8  | 1    | 锁相模式           |
| saw_freq_hz | uint32 | 4    | 锯齿波频率，单位Hz |

Payload总长度：

```
7字节
```

## lock_mode定义

| 数值   | 模式         |
| ------ | ------------ |
| `0x00` | 0°锁相       |
| `0x01` | -90°锁相     |
| `0x02` | 二倍频0°锁相 |

## saw_freq_hz

虽然现在只有1kHz和10kHz，仍然建议直接传实际频率，而不是只传枚举值：

```
1000  Hz
10000 Hz
```

这样以后增加2kHz、5kHz等频率时，不需要修改协议。

OpenMV收到后应检查：

```
lock_mode是否合法
saw_freq_hz是否为1000或10000
当前是否空闲
```

检查通过后立即返回ACK，然后再开始图像识别。

------

## 示例帧

假设：

```
协议版本：1
TYPE：0x10
SEQ：1
session_id：1
lock_mode：0°
锯齿波频率：1000Hz
```

Payload为：

```
01 00       session_id = 1
00          mode = 0°
E8 03 00 00 saw_freq = 1000Hz
```

完整数据帧：

```
AA 55 01 10 01 07 00 01 00 00 E8 03 00 00 6F 94
```

其中：

```
CRC16 = 0x946F
```

CRC按照小端序发送，所以是：

```
6F 94
```

# 八、OpenMV返回粗识别结果

OpenMV完成波峰计数、拖尾去除和倍数判断后，返回该消息。

## 消息类型

```
TYPE = 0x11
```

## Payload格式

| 字段             | 类型   | 长度 | 说明                     |
| ---------------- | ------ | ---- | ------------------------ |
| session_id       | uint16 | 2    | 当前任务号               |
| result           | uint8  | 1    | 识别状态                 |
| ratio_x1000      | uint32 | 4    | 未知频率与锯齿波频率之比 |
| confidence       | uint8  | 1    | 置信度0～100             |
| left_peak_count  | uint8  | 1    | 左侧识别波峰数           |
| right_peak_count | uint8  | 1    | 右侧识别波峰数           |

Payload总长度：

```
10字节
```

## result定义

| 数值   | 含义                   |
| ------ | ---------------------- |
| `0x00` | 识别成功               |
| `0x01` | 识别成功，但置信度较低 |
| `0x02` | 没有检测到有效曲线     |
| `0x03` | 左右识别结果差异过大   |
| `0x04` | 绿色拖尾干扰严重       |
| `0x05` | 图像过曝或欠曝         |
| `0x06` | 识别超时               |
| `0x07` | 任务被取消             |

## 倍数表示方法

不建议在STM32和MicroPython之间直接传浮点数，因为不同平台的结构体对齐和浮点格式容易带来问题。

采用放大1000倍的整数：

```
ratio_x1000 = 未知频率 / 锯齿波频率 × 1000
```

例如：

| 实际倍数 | ratio_x1000 |
| -------- | ----------- |
| 1倍      | 1000        |
| 2倍      | 2000        |
| 3.5倍    | 3500        |
| 8.246倍  | 8246        |

STM32预测未知信号频率：

```
estimated_freq_hz =
    saw_freq_hz * ratio_x1000 / 1000;
```

例如：

```
锯齿波频率 = 1000Hz
ratio_x1000 = 5200
```

则：

```
未知频率约为 5200Hz
```

左右波峰数用于调试。后续正式版本不需要时，可以将其固定为0，或者通过协议版本删除。

STM32收到粗识别结果后，应立即向OpenMV返回ACK。

------

# 九、DDS频率测试命令

STM32根据粗识别结果计算初始DDS搜索范围，然后：

1. 设置AD9910输出频率；
2. 等待DDS和示波器显示基本稳定；
3. 把本次设置的频率发送给OpenMV。

## 消息类型

```
TYPE = 0x20
```

## Payload格式

| 字段             | 类型   | 长度 | 说明               |
| ---------------- | ------ | ---- | ------------------ |
| session_id       | uint16 | 2    | 当前任务号         |
| test_id          | uint16 | 2    | 本次频率测试编号   |
| dds_freq_hz      | uint32 | 4    | DDS当前频率        |
| search_stage     | uint8  | 1    | 当前搜索阶段       |
| capture_delay_ms | uint16 | 2    | OpenMV等待后再拍摄 |

Payload总长度：

```
11字节
```

## test_id

每测试一个新频率加1：

```
1、2、3、4……
```

它非常重要，因为即使串口重发，OpenMV也能知道这是：

- 同一个频率测试的重复命令；
- 还是一次新的频率测试。

## search_stage定义

| 数值   | 含义           |
| ------ | -------------- |
| `0x00` | 粗搜索         |
| `0x01` | 中等步长搜索   |
| `0x02` | 精细搜索       |
| `0x03` | 最终确认       |
| `0x04` | 锁相阶段，预留 |

## capture_delay_ms

OpenMV收到命令后，不必立即识别，可以等待一段时间，让示波器图形稳定：

```
建议初始值：100～300ms
```

实际值根据示波器刷新速度调整。

OpenMV收到后立即返回ACK，然后执行：

```
等待capture_delay_ms
连续采集若干帧
进行图像判断
返回识别结果
```

# 十、DDS频率识别结果

## 消息类型

```
TYPE = 0x21
```

## Payload格式

| 字段        | 类型   | 长度 | 说明            |
| ----------- | ------ | ---- | --------------- |
| session_id  | uint16 | 2    | 当前任务号      |
| test_id     | uint16 | 2    | 对应的测试编号  |
| result      | uint8  | 1    | 频率识别结果    |
| match_score | uint16 | 2    | 匹配分数0～1000 |
| confidence  | uint8  | 1    | 置信度0～100    |

Payload总长度：

```
8字节
```

## result定义

| 数值   | 名称           | 含义                       |
| ------ | -------------- | -------------------------- |
| `0x00` | TARGET_REACHED | 已达到目标频率             |
| `0x01` | DDS_TOO_LOW    | DDS频率偏低                |
| `0x02` | DDS_TOO_HIGH   | DDS频率偏高                |
| `0x03` | NOT_MATCHED    | 未达到目标，但无法判断方向 |
| `0x04` | UNSTABLE       | 图像仍在运动或不稳定       |
| `0x05` | LOW_CONFIDENCE | 判断置信度过低             |
| `0x06` | IMAGE_ERROR    | 没有识别到有效图形         |
| `0x07` | TIMEOUT        | 识别超时                   |

如果当前算法只能识别“到达”或“未到达”，就先只使用：

```
0x00 TARGET_REACHED
0x03 NOT_MATCHED
```

后面如果能根据图形运动方向判断DDS偏高还是偏低，再启用：

```
0x01 DDS_TOO_LOW
0x02 DDS_TOO_HIGH
```

这样协议不用重新设计。

## match_score

建议定义为：

```
0：完全不匹配
1000：完全匹配
```

是否认为达到目标，不要只看单帧，建议OpenMV内部连续判断，例如：

```
连续5帧中至少4帧：
match_score ≥ 850
```

才返回：

```
TARGET_REACHED
```

这样能减少偶然误判。

STM32收到该结果后，立即返回ACK。

# 十一、停止任务命令

当满足以下情况时，STM32可以主动停止OpenMV当前任务：

- 用户取消；
- 搜索次数超过上限；
- 找到目标频率；
- 需要重新开始；
- 通信或图像异常。

## 消息类型

```
TYPE = 0x22
```

## Payload格式

| 字段       | 类型   | 说明         |
| ---------- | ------ | ------------ |
| session_id | uint16 | 要终止的任务 |
| reason     | uint8  | 停止原因     |

`reason`建议：

| 数值   | 含义         |
| ------ | ------------ |
| `0x00` | 正常完成     |
| `0x01` | 用户取消     |
| `0x02` | 搜索超时     |
| `0x03` | 搜索次数超限 |
| `0x04` | 重新开始     |
| `0x05` | 系统错误     |

OpenMV收到后：

1. 停止当前识别；
2. 清除缓存结果；
3. 返回ACK；
4. 回到空闲状态。

# 十二、完整通信流程

推荐的正常通信顺序如下：

```
STM32                                OpenMV
  |                                    |
  |---- START_TASK 0x10 -------------->|
  |<------------- ACK 0x01 ------------|
  |                                    |
  |          OpenMV粗识别               |
  |                                    |
  |<------- COARSE_RESULT 0x11 --------|
  |------------- ACK 0x01 ------------>|
  |                                    |
  | STM32计算预测频率和搜索范围         |
  | STM32设置DDS频率                    |
  |                                    |
  |------- DDS_TEST 0x20 -------------->|
  |<------------- ACK 0x01 ------------|
  |                                    |
  |       OpenMV识别当前图像             |
  |                                    |
  |<----- DDS_TEST_RESULT 0x21 --------|
  |------------- ACK 0x01 ------------>|
  |                                    |
  | STM32判断是否继续搜索               |
  |                                    |
  |------- DDS_TEST 0x20 -------------->|
  |<------------- ACK 0x01 ------------|
  |<----- DDS_TEST_RESULT 0x21 --------|
  |------------- ACK 0x01 ------------>|
  |                                    |
  |           ……继续尝试……              |
  |                                    |
  |<--- result = TARGET_REACHED --------|
  |------------- ACK 0x01 ------------>|
  |                                    |
  |------- STOP_TASK 0x22 ------------>|
  |<------------- ACK 0x01 ------------|
  |                                    |
  |       进入后续相位锁定阶段           |
```

# 十三、双方状态机

## STM32状态机

```
IDLE
  ↓
SEND_START_TASK
  ↓
WAIT_START_ACK
  ↓
WAIT_COARSE_RESULT
  ↓
CALCULATE_SEARCH_RANGE
  ↓
SET_DDS_FREQUENCY
  ↓
SEND_DDS_TEST
  ↓
WAIT_DDS_TEST_ACK
  ↓
WAIT_DDS_TEST_RESULT
  ├── 未达到目标 → 调整DDS → SEND_DDS_TEST
  ├── 图像异常   → 重试或终止
  └── 达到目标   → FREQUENCY_LOCKED
                         ↓
                   PHASE_LOCK_STAGE
```

## OpenMV状态机

```
IDLE
  ↓ 收到START_TASK
COARSE_RECOGNIZING
  ↓ 返回粗识别结果
WAIT_DDS_TEST
  ↓ 收到DDS_TEST
DDS_RECOGNIZING
  ├── 返回未达到 → WAIT_DDS_TEST
  ├── 返回图像异常 → WAIT_DDS_TEST
  └── 返回达到目标 → FREQUENCY_FOUND
```

OpenMV在 `DDS_RECOGNIZING` 状态下如果又收到新的DDS测试命令，可以返回：

```
NACK：BUSY
```

初版协议不建议连续发送多个测试频率，也就是不要做流水线。必须收到上一个频率的识别结果后，再发送下一个频率。

# 十四、超时和重发机制

建议参数：

| 项目               | 建议值 |
| ------------------ | ------ |
| ACK超时            | 100ms  |
| ACK最大重发次数    | 3次    |
| 粗识别结果超时     | 5s     |
| DDS识别结果超时    | 2s     |
| 结果包ACK超时      | 100ms  |
| 结果包最大重发次数 | 3次    |

例如STM32发送 `DDS_TEST`：

```
发送DDS_TEST
等待100ms
```

如果没有收到ACK：

```
使用相同的TYPE、SEQ、session_id、test_id重发
```

注意必须使用相同SEQ，OpenMV才能判断它是重发，而不是新的测试。

# 十五、重复包处理

这是协议里很关键的一点。

假设：

1. OpenMV已经收到 `DDS_TEST`；
2. OpenMV发送了ACK；
3. ACK在传输中丢失；
4. STM32重新发送相同命令。

OpenMV发现：

```
TYPE相同
SEQ相同
session_id相同
test_id相同
```

此时不能重新启动一次识别，而应当：

- 如果识别还未完成：重新发送ACK；
- 如果识别已经完成：发送ACK，并重新发送之前缓存的识别结果。

因此OpenMV建议至少缓存：

```
last_rx_type
last_rx_seq
last_session_id
last_test_id
last_result_packet
```

STM32同样要缓存当前等待确认的数据包。

# 十六、串口接收解析建议

双方都不要假设一次串口接收正好对应一帧。串口可能出现：

```
半包
粘包
一次收到多包
杂乱字节
```

正确解析流程：

```
1. 在接收缓存中寻找 AA 55
2. 判断是否已经收到7字节基础帧头
3. 读取LEN
4. 如果LEN > 64，丢弃当前帧头
5. 等待完整帧：7 + LEN + 2 字节
6. 校验CRC
7. CRC正确则执行消息
8. CRC错误则丢弃，并继续寻找下一个 AA 55
```

协议采用长度字段，因此Payload中即使出现：

```
AA 55
```

也不需要转义。

不要在STM32中直接通过强制类型转换解析结构体，例如：

```
Packet_t *packet = (Packet_t *)buffer;
```

这可能受到结构体填充和对齐影响。建议逐字节读取：

```
session_id = buffer[index] |
             ((uint16_t)buffer[index + 1] << 8);
```

OpenMV端则可以使用：

```
struct.pack("<H", value)
struct.pack("<I", value)

struct.unpack("<H", data)
struct.unpack("<I", data)
```

其中 `<` 表示小端序。

# 十七、建议保留的相位锁定接口

虽然锁相逻辑还没确定，但协议现在就可以预留：

```
0x30 PHASE_LOCK_START
0x31 PHASE_LOCK_RESULT
0x32 PHASE_ADJUST
0x33 PHASE_LOCK_FINISHED
```

后面可能的相位识别结果可以设计为：

```
PHASE_OK
PHASE_LEADING
PHASE_LAGGING
PHASE_UNSTABLE
IMAGE_ERROR
```

相位误差可以使用：

```
int16_t phase_error_x100
```

例如：

```
+12.35° → 1235
-90.00° → -9000
```

但现在暂时不启用，先把频率粗识别和DDS搜索流程跑通。

# 十八、最终建议采用的最小消息集合

第一版程序实际只需要实现这6种包：

```
0x01 ACK
0x02 NACK
0x10 START_TASK
0x11 COARSE_RESULT
0x20 DDS_TEST
0x21 DDS_TEST_RESULT
```

第一版流程可以简化成：

```
START_TASK
    ↓
COARSE_RESULT
    ↓
DDS_TEST
    ↓
TARGET_REACHED / NOT_MATCHED
    ↓
不断调整DDS
    ↓
TARGET_REACHED后停止
```

协议层面已经把偏高、偏低、相位锁定、调试数据等扩展位置留好了，后续算法变化时不需要推翻重写。
